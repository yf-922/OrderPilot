# 客服 Agent：评测证据与本地性能报告

整理日期：2026-10-20。本文区分真实模型实验、检索评测与本地 HTTP 压测，不将不同分母的数据拼接成综合提升。本次整理没有新调用付费模型。

## 结论与使用口径

- **上下文压缩有实测收益**：历史实验的三条完整配对对话中，纯压缩累计输入减少 52.24%，压缩加规则减少 57.90%。这些是小样本描述性结果。
- **Go 规则可以省主模型调用**：有效确认由后端直接完成。但“一条八轮对话少调用主模型一个用户轮”是 12.5% 的用户轮绕过率，不等于全部 API 请求或无效工具减少 12.5%。
- **官方 Jev 尚无额外效率收益证据**：独立三组实验中，相比规则版，计入官方 Jev 自身用量后输入增加 7.22%，平均响应增加 27.68%。示例默认关闭外部 Jev。
- **本地性能不等于线上模型性能**：下面的 HTTP 压测只衡量本机控制器、鉴权与本地 Agent，不能用其 RPS 推导远程模型承载量。

## 历史真实模型上下文消融

证据：[最终报告](strict-core4-v3-resumed/final-resumed-report.md)、[汇总 JSON](strict-core4-v3-resumed/final-resumed-summary.json)、[续跑 Checkpoint](strict-core4-v3-resumed/checkpoint.json)、[续跑审计](strict-core4-v3-resumed/continuation-audit.json)。

四组为完整历史/规则关（A）、完整历史/规则开（B）、三级压缩/规则关（D）、三级压缩/规则开（E）。这里的 Jev_On 指 Go 规则，不是官方 TypeSafe 模型。采用相同场景和业务 fixture，自由运行端到端，不是每轮固定 Gold History 的 Teacher Forcing；生成历史可能不同。

四条八轮场景中，一条存在 Provider 中断，因此效率主比较采用三条全部组别完整配对场景 S2/S3/S4，不删除失败记录：

旧报告中出现的“平均延迟降低 33.7%”属于固定历史回放口径，不能与上述端到端 Token 数据合并为一次线上结论。完整历史增长取决于每轮载荷；本项目没有证明其指数增长。

## 官方 Jev 三组独立验证

2026-10-17，主模型 `gpt-6.1-sol`，官方 `jev-1.13.0`。两条八轮对话，三组各 16 个用户轮，串行交错，固定 Mock 工具和 RAG，无自动重试。92 次真实模型请求：主模型 87 次、Jev 5 次。

| 每用户轮 Jev 耗时均值 | 0 | 约 0ms | 318.38ms |

Token 来自 Provider usage，包含未采用的 Jev 判断。Jev 自身输入 5,853、输出 1,155，实际采用 2 次、回退 3 次。Jev 单次平均约 1.019s，表中的 318.38ms 是摊到 16 个用户轮后的值。R/J 最终确认均由 Go 规则直通，不能归功于官方模型。

R 相对 C 输入减少 14.96%；J 相对 R 输入增加 7.22%。慢请求主要在主模型网络阶段，J 组最慢轮没有调用官方 Jev，因此不能把所有慢响应归因于 Jev。C 返回缓存输入 2,048 Token，R/J 为 0，但没有冷热缓存对照，不能断言 Prefix Cache 是因果原因。

三组总用量 219,449 Token。网关单价未知，不虚构美元总成本。两条对话不足以证明总体准确率 100%、显著速度差异或生产 P95 SLA。

## 本地 HTTP 并发压测

### 环境与方法

- 时间：2026-10-20；Go 1.27.0，Windows/amd64，20 逻辑 CPU，GOMAXPROCS=20。
- 链路：真实 loopback HTTP → Iris → Bearer 鉴权 → AgentController → 共享 Agent Service → 本地确定性 Provider。
- 场景一：政策问答触发一次本地知识检索并回答。场景二：投诉直接返回人工交接信息，不调用工具。
- 每行预热 20 次后统计 10,000 次；并发 1、8、32；共 60,000 次统计请求，另 120 次预热。
- 闭环客户端，每个 worker 完成上一个请求才发下一个；每次创建独立会话，响应后清理会话。清理不计入单次延迟，但计入总墙钟吞吐。
- 延迟从发送 HTTP 到完整读取响应，不含客户端解码和清理；P50/P95/P99 用 nearest-rank 计算。
- 失败包含非 200、读响应/JSON 错误、状态不符、回复为空、工具数量不符或工具执行失败，不只检查 HTTP 状态码。
- **不包含 MySQL、Redis、远程主模型、Embedding、官方 Jev 或真实 Tokenizer；也不覆盖多轮长会话。**

## 已知工程边界

1. Tokenizer 对 `messages + tools` JSON 使用固定编码计数，不等于 Provider 内部消息封装的计费口径；计数失败有估算回退，极小预算紧急降级没有最终复核。因此当前不能承诺全路径严格硬预算。状态锚点也尚无全面 80 Token 硬上限证明。
2. 压缩先应用用户轮次窗口，再继续缩预算；摘要是代码提取用户诉求、数字候选和助手结论，并非语义无损摘要。需要实时信息时必须再查工具。
3. Chat 当前未实际执行并填入 RAG 预检分数；`RAGTopScore` 默认值不能解释为已校准的检索置信度。
4. 已查询的订单候选并非全部本人订单，不能仅凭候选之外就证明越权；后端执行层的归属校验仍是最终安全边界。
5. Redis 保存状态快照，完整消息仍在内存；尚不支持完整会话跨重启恢复。同会话并发也未实现线性一致，版本号不等于会话锁。
6. 人工交接仅生成结构化信息，没有真实坐席接单、客服工单 SLA 或支付退款流程。

## 可用于简历的谨慎表述

> 面向多轮订单咨询与取消场景，使用 Go 规则前置判断确认、重复操作和人工升级，结合结构化状态、历史工具字段脱水与安全轮次裁剪。在三条完整配对的八轮真实模型对话中，组合方案累计输入 Token 降低 57.9%、Turn 6+ 单请求峰值降低 66.1%；另构建 30 条客服挑战集，工具路径正确率为 27/30。保留原始调用记录及失败样本，区分最终业务完成与严格工具轨迹指标。

本地压测如需写入简历，应另注明“本地确定性 Provider、无数据库及远程模型”，不要写为生产万级 QPS。
